## M21.1 — The local game store

**Status:** DONE

**Depends on:** None

### Objective

Add the project's SQLDelight local-game store (`D084`, `D085`) to `chess-app`: the
schema, the repository and the backup exclusion. Nothing the player sees changes
yet; `M21.2` moves pass-and-play onto it.

### Acceptance Criteria

- **Storage.**
  - SQLDelight is added through the version catalog, with the database in
    `chess-app` and schema versioning and migrations from the first version.
  - The tables are `local_games` and `local_moves`, shaped as in `D084`, and nothing
    else.
  - SQLDelight models and persistence DTOs stay out of `chess-core`.
- **One unfinished game.** At most one `ACTIVE` local game exists, of any kind, and
  any number of `COMPLETED` ones. The repository enforces this, and so does a database
  constraint where that is straightforward. The repository owns the replacement flow:
  replacing the unfinished game deletes it.
- **Writes append and truncate.**
  - A move appends its record and updates the state.
  - An undo removes the latest record and restores the recorded prior position.
  - Each change touching state and history is one SQLDelight transaction.
  - The whole history is never rewritten.
- **Completion.** A game that ends changes from `ACTIVE` to `COMPLETED` and is kept.
- **Restoring** rebuilds `ChessGame(state, history)` from the stored state and move
  records. It never replays moves through the rules (`D029`, `D061`).
- **Not backed up.** The local-game database is excluded from Android cloud backup and
  from device transfer, in both `backup_rules.xml` and `data_extraction_rules.xml`.
- **Tests — storage and repository:**
  - save and load a new game, and a game after ordinary moves;
  - round trips with castling, en passant and promotion;
  - repetition counts and draw-claim availability survive restoring;
  - undo after reloading;
  - the repository is recreated, as after process death;
  - a move and its history append are atomic;
  - an undo's state restore and history truncation are atomic;
  - only one `ACTIVE` game can exist;
  - a replaced unfinished game is deleted, not kept in history;
  - a finished game is kept, several finished games coexist, and they come back
    newest first;
  - the backup and data-extraction rules name the database file.
- `ARCHITECTURE.md` §11.4 describes what was built. `DEVELOPMENT.md` gains any command
  or note SQLDelight needs.

### Verification

- The storage tests.
- `.\gradlew.bat build`.
- `git diff --check`.

2026-10-01. `com.jmussel.chessgame.local`: `LocalGameStore` over the SQLDelight
`LocalGameDatabase` (`LocalGames.sq`, `LocalMoves.sq`), `LocalStateDocument` for
positions, and `openLocalGameStore(context)` for `local_games.db`. Nothing calls it yet;
`M21.2` does. `ARCHITECTURE.md` §11.4 describes what was built.

- **Constraints.** A unique partial index allows one `ACTIVE` row. `CHECK`s tie status

## M21.5 — `chess-ai`: the `ChessEngine` interface and the project's Kotlin engine

**Status:** DONE

**Depends on:** None

### Objective

Create `chess-ai` (`D086`): a pure Kotlin/JVM module holding the chess-specific
`ChessEngine` interface and the project's first engine, independent of any Android
code.

### Acceptance Criteria

- **The module.**
  - `chess-ai` is in `settings.gradle.kts`, applies the Kotlin/JVM plugin only, and
    depends on `chess-core` only.
  - ktlint and its tests run in `./gradlew build`.
  - Nothing but `chess-app` will depend on it.
- **The interface.** `ChessEngine` is chess-specific. Its contract is `D086`'s:
  - a legal move for any unfinished position with a legal move;
  - a legal fallback settled before searching deeper;
  - cancellable, and cancellation applies no move;
  - runs off the main thread;
  - seedable randomness;
  - never asked to move in a finished game.
- **The engine.**
  - Alpha-beta search over `chess-core`'s legal moves.
  - Material plus simple positional evaluation.
  - Three difficulty levels.
  - A time budget.
  - This task chooses and records the depths and budgets.
- **Tests:**
  - it never returns an illegal move;
  - a position with only one legal move;
  - promotion positions;
  - mate in one found at the levels expected to find it;
  - the higher levels take an obviously hanging queen;
  - deterministic under a fixed seed;
  - normal completion respects the budget;
  - cancellation ends without a move to apply;
  - it is not invoked on a finished game.

  Tests do not pin one exact move where several are reasonable.
- `ARCHITECTURE.md` §4 lists `chess-ai` as built, and `DEVELOPMENT.md` gains its test
  command.

### Verification

- `.\gradlew.bat :chess-ai:test`.
- `.\gradlew.bat build`.
- `git diff --check`.

### Completion Note

2026-10-01. New module `chess-ai` (Kotlin/JVM plugin, `chess-core` only, in
`settings.gradle.kts` for every build including `-PserverOnly`). It holds
`ChessEngine`, `Difficulty` (levels 1–3, `ofLevel`) and `AlphaBetaEngine`:
iterative deepening from a legal fallback, alpha-beta over `ChessRules`, captures and
promotions ordered first, and material plus simple positional evaluation. `D088`
records the levels: depth 1, 2 and 3; budgets 0.5, 1.5 and 3 s; random choice within

## M21.6 — Computer turns and takeback

**Status:** DONE

**Depends on:** M21.1, M21.5

### Objective

Build the logic of a game against the computer (`D086`) below the UI: whose turn it
is, running the engine, discarding stale results, takeback, and saving. `M21.7` adds
the entry points and screens.

### Acceptance Criteria

- **The computer's turn.**
  - The human can move only on their own turn.
  - The search runs off the main thread, and exactly one valid search owns each
    computer turn.
  - Leaving the game cancels work that no longer needs to run.
  - Resuming a game on the computer's turn starts exactly one search.
  - A stale, cancelled or superseded result is discarded and never changes a game.
- **Storage.**
  - Games are saved through `M21.1`'s store, with `kind = COMPUTER`, the difficulty
    and the human's colour.
  - Every accepted move, human or computer, is saved in one transaction.
- **Takeback, exactly as `D086`:**
  - after a reply, it takes back the reply and the human move before it;
  - while the computer is thinking, it cancels the search and takes back the human
    move alone;
  - it can be repeated back to the player's first move;
  - it is unavailable once the game has ended.
- **Draws and resignation, as `D086`.** The human may resign and make legal draw
  claims. The computer never resigns, offers or claims a draw.
- **Game end.** The game becomes `COMPLETED` and is kept.
- **Tests, with a deterministic fake `ChessEngine`:**
  - a human move triggers exactly one reply;
  - a game-ending human move triggers no engine call;
  - a game-ending computer move completes the game;
  - input is disabled on the computer's turn;
  - two-move takeback after a reply;
  - one-move takeback while the computer is thinking;
  - a cancelled search cannot apply its result;
  - replacing the game stops an old search from changing the new one;
  - takeback is unavailable after the game ends;
  - reopening on the computer's turn starts exactly one search;
  - a finished computer game is kept.

### Verification

- The `chess-app` unit tests for the computer game.
- `.\gradlew.bat build`.
- `git diff --check`.

### Completion Note

2026-10-01. `chess-app` depends on `chess-ai`. `ComputerGame` (package `computer`),
owned by `ChessAppViewModel.computerGame`, holds a game against the computer:
`resume`, `start(opponent)`, `update(board)` for the human's taps, `takeBack`,
`leave`. `ChessAppDependencies` gains `chessEngine` (an `AlphaBetaEngine` seeded per
launch) and `engineDispatcher` (`Dispatchers.Default`). `ARCHITECTURE.md` §11.4
describes it. There is no screen or entry yet; `M21.7` adds them.

- **One search per turn.** Starting a search cancels any other; leaving cancels it.
  The engine's `isCancelled` reads the coroutine's `isActive`.
- **Stale results.** Each search carries a turn number and its game, and its move is
  applied only if both are still current. Cancellation alone is not relied on.
- **Input.** On the computer's turn the board ignores the human, except a
  resignation. Claims and resignation for the computer are refused.
- **Takeback** is two plies after a reply and one while thinking, built from
  `ChessRules.undoLastMove`. It is offered only in an unfinished game with a human move
  to take back.
- **`LocalGameSession`** now takes the stored game's id on every save, and returns the
  stored game from `resume` and `startNew(computer)`. It also gains `resumeComputer`.

Verified:

- `ComputerGameTest` (15), with scripted fake engines and a real store: exactly one
  reply per human move; the computer opens when the human is Black; a game-ending human
  move calls no engine; a game-ending computer move completes and keeps the game with
  its opponent; the board ignores the human while the computer thinks; leaving stops
  the search, and reopening twice starts exactly one; two-ply takeback; repeated back to
  the human's first move and no further; one-ply takeback while thinking; a result that
  arrives after cancellation is discarded; replacing the game protects the new one;
  takeback is unavailable after the end; the human may resign while the computer
  thinks but cannot resign for it; the human may claim a draw and the computer never
  does.
- Mutations: without cancelling the search, the turn and game check still discards

  stale-result test fails as well.
- `.\gradlew.bat build`: BUILD SUCCESSFUL. `chess-app` debug unit tests: 605, none

  - it is their turn;
  - the latest move is the opponent's;
  - the move before it is theirs;
  - they have no undo request pending in this game.

  Otherwise the request is refused with a typed result and no change. It is sent with
  `expectedVersion`, like every command, and increments the version.
- **Accepting.** Only the opponent may accept.
  - Accepting restores the position before the requester's move, with the requester to
    move: `ChessRules.undo` for the opponent's side, then for the requester's. Nothing is
    replayed (`D061`).
  - It succeeds only at the version the request was made at. An earlier version is
    refused as stale.
  - It increments the version once, and clears the request.
- **The opponent's Undo counts as accepting.** While an undo request waits on the
  opponent, the existing undo command from the opponent, at the request's version, is
  an accept: both moves are undone, `UndoAccepted` is recorded, and the requester is
  told it was accepted.
- **Crossing.** A request and the opponent's undo sent at the same moment are combined,
  in either order, ending at the position before the requester's move:
  - the opponent's undo, stale by exactly the request, accepts it;
  - the request, stale by exactly the opponent's undo, undoes the requester's move.

  "Stale by exactly" means: the command's `expectedVersion` is the version the other
  command was applied to, and that command is the only change since. Anything else in
  between leaves the command stale and refused. The game row records the last accepted
  change (kind, actor, version applied to) for this check; the audit trail is not read.
  Notes and audit events follow what happened:
  - **Request first:** the requester sees the accepted note. The opponent sees "Jordan
    had asked to undo g1f3, so both moves were undone". Audit: `UndoRequested`, then
    `UndoAccepted`, marked as a crossing.
  - **Undo first:** the requester sees "Alex had undone b8c6, so g1f3 was undone too".
    The opponent sees the same note as above. Audit: `MoveUndone`, then
    `UndoRequested`, completed at once and marked as a crossing, with no
    `UndoAccepted`.

  Each command increments the version once.
- **Declining.** Only the opponent may decline. It clears the request and increments the
  version. The requester may ask again at once. After a decline, the opponent's undo
  undoes their reply alone again (`D016`).
- **No confirmation.** Accept and Decline each take one tap.
- **The answer.** The game keeps the last answer (accepted or declined), or the last
  crossing, until the next accepted change to the game. Each note shows until then,
  including on opening the game later, never just once.
- **The requester can still play.** While the request waits, the requester's board stays
  playable, and a move withdraws the request.
- **Clearing.** Every other accepted command clears a pending request in the same
  transaction: a move, a draw claim or a resignation by either player. The requester
  has no cancel, and nothing expires on a timer. A finished game never has a request
  pending.
- **Not a clearing change.** Leaving the series is not a game command (`D068`), so it
  leaves a pending request in place.
- **Stale by design.** Asking increments the version. So any other command from the
  opponent sent at the same moment (a resignation, for instance) is refused as stale
  and their screen refreshes. That is the existing handling, and it is not a bug.
- **Activity.** Request, accept and decline each record the actor's last action
  (`recordAction`, `M19.11`).
- **Persistence.** The pending request, the last answer and the last accepted change
  are stored with the game row (one forward-only migration, safe on live data), not in
  `GameState` or `GameStateDocument`. `chess-core` is unchanged. Request, accept and decline each write
  an audit event that names its actor and series (`D078`).

## M21.21 — Redo

**Status:** DONE

**Depends on:** M21.19, M21.20

### Objective

Add a plainly labelled **Redo** button to pass-and-play, games against the computer,
and online games (`D092`). Redo restores exactly what the preceding accepted Undo or
takeback operation removed. Its complete forward path is persistent game state, not
temporary screen or ViewModel state.

### Acceptance Criteria

- **All playable modes.** Redo works in:
  - pass-and-play;
  - games against the computer;
  - online games.
- **One operation per accepted Undo or takeback.** One tap restores one operation:
  - pass-and-play Undo removes and Redo restores one ply;
  - a normal unilateral online Undo removes and Redo restores one ply;
  - a computer takeback that removed a human move and its recorded computer reply is
    restored as that same two-ply operation, atomically;
  - a computer takeback made before a reply existed restores its human move alone;
  - an accepted or crossed online undo request restores its exact two plies atomically.
- **The entire path is retained.** Use an active-history cursor, or an equivalent
  ordered retained suffix with operation boundaries:
  - Undo moves backward without deleting the later recorded moves;
  - Redo moves forward through those exact operations in their original order;
  - repeated Undo retains every operation ahead;
  - alternating Undo and Redo retains the remaining forward path.
- **Persistent, not screen-local.** Availability and the complete path survive Back
  and reopening the game, rotation and ordinary state recreation, process death, and
  app restart. For online games they are canonical server state and also survive
  reopening the game from another client installation.
- **Exact recorded restoration.** Redo restores recorded moves and recorded resulting
  states. It never reconstructs canonical state by replaying commands through the
  rules. Each retained move preserves enough information to restore its exact:
  - board;
  - side to move;
  - castling rights;
  - en passant target;
  - halfmove clock;
  - repetition counts;
  - result state where applicable.
- **A new branch clears the path.** Any ordinary newly accepted move clears every
  remaining Redo operation in the same transaction. A move is a continuation only
  when the Redo command applies it; manually playing the same coordinates is still a
  new branch and clears the path.
- **Final actions clear and stay final.** Resignation, a successful draw claim, and a
  newly played game-ending move clear the remaining path in the same transaction.
  They cannot be undone or redone past (`D017`–`D019`), and no finished game offers
  Redo.
- **Activity that does not change history does not clear it.** Navigation, refresh,
  reconnect, opening another screen, rotation, process recreation, app restart, and
  undo-request status changes that do not alter move history leave the path intact.
  Accepting or crossing an undo request adds its two-ply operation. Redo itself is a
  board-changing command and clears any pending request or last-answer note under
  `D091`'s existing next-change rule.
